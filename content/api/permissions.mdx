# Permissions & groups

Manage **groups**, **user ↔ group membership**, and **warehouse access** for tables and views. Callers use these endpoints to grant Read / ReadWrite (and related levels) the same way the product Admin and warehouse permission sidebars do.

> **Base:** `/api/v1`  
> **Auth:** `Authorization: Bearer {token}`  
> **Scopes:** `permissions:read` / `permissions:write` (plus `warehouses:read` when resolving warehouse context)

Today these operations run through ProcessServer (screen access, roles/groups, view roles). Public REST wraps them under `/groups`, `/users`, and `/warehouses/.../access`.

---

## How access works

| Resource | Who you grant | What it controls |
| --- | --- | --- |
| **Group** | Named org group (internally a role) | Membership + optional component-level rights |
| **User ↔ group** | Users as members of groups | Inheritance — users pick up every table/view grant on their groups |
| **Table (screen access)** | Groups → permission level on a warehouse table/entity | Who can see / use the table in CoSet DB |
| **View** | Groups → permission level; optional **owners** (users) | Who can open / edit the view; owners get full access |

**Permission levels** used for table and view grants:

| `access` | Meaning |
| --- | --- |
| `no_rights` | Explicit deny / no match (usually only on effective-permission responses) |
| `read_only` | Browse / query |
| `read_write` | Browse and change (edit definition, manage related settings where applicable) |

Table screen-access policies are **group-based**. Assign users to groups to give them table access. Views support **group grants** and **owner users**.

File-store ACLs stay on [File stores](./file-stores) (`PermissionRule`). Credential group ACLs stay on [Credentials](./credentials).

## Shared types

### `GroupSummary`

| Field | Type | Description |
| --- | --- | --- |
| `id` | `integer` | Group ID |
| `name` | `string` | Display name |
| `description` | `string \| null` | |
| `member_count` | `integer \| null` | When known |
| `is_admin` | `boolean` | Admin / elevated group |
| `created_at` | `string` | ISO 8601 |
| `updated_at` | `string \| null` | ISO 8601 |

### `GroupDetail`

Extends `GroupSummary`:

| Field | Type | Description |
| --- | --- | --- |
| `user_ids` | `integer[]` | Member user IDs |
| `component_permissions` | `ComponentPermission[]` | Optional org-component levels |

### `ComponentPermission`

| Field | Type | Description |
| --- | --- | --- |
| `component` | `string` | e.g. `data_warehouse`, `database_views`, `screen_access` |
| `access` | `string` | `read_only` / `read_write` / … |

### `UserSummary`

| Field | Type | Description |
| --- | --- | --- |
| `id` | `integer` | User ID |
| `email` | `string` | |
| `display_name` | `string \| null` | |
| `is_enabled` | `boolean` | |
| `group_ids` | `integer[]` | Groups the user belongs to |

### `AccessGrant`

One row in a table or view ACL.

| Field | Type | Description |
| --- | --- | --- |
| `principal_type` | `string` | `group` (required for table policies). Views also use `group`; owners are listed separately as users |
| `principal_id` | `integer` | Group ID |
| `access` | `string` | `read_only` or `read_write` |

### `TableAccessPolicy`

| Field | Type | Description |
| --- | --- | --- |
| `warehouse_id` | `integer` | |
| `table_name` | `string` | Entity / table name the policy applies to |
| `grants` | `AccessGrant[]` | Group → level |
| `updated_at` | `string \| null` | ISO 8601 |

### `ViewAccessPolicy`

| Field | Type | Description |
| --- | --- | --- |
| `warehouse_id` | `integer` | |
| `view_name` | `string` | Schema-qualified or view name as returned by list views |
| `grants` | `AccessGrant[]` | Group → level |
| `owner_user_ids` | `integer[]` | Users with full access (bypass group ACL) |
| `updated_at` | `string \| null` | ISO 8601 |

### `PUT /users/{userId}/groups`

Replace the user’s group membership. This is the primary way to give a **user** table access: put them in the groups that hold the table grants.

| | |
| --- | --- |
| **Status** | Planned (today: `UpdateAccountUser` with `UserGroups`) |
| **Scopes** | `permissions:write` |

#### Request body

```json
{
  "group_ids": [12, 18]
}
```

#### Response `200 OK`

```json
{
  "id": 101,
  "email": "ops.lead@example.com",
  "display_name": "Ops Lead",
  "is_enabled": true,
  "group_ids": [12, 18]
}
```

You can also set membership from the group side via [`PATCH /groups/{groupId}`](#patch-groupsgroupid) (`user_ids`).

### Example

```bash
curl -sS -X PUT \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"group_ids":[12,18]}' \
  "https://{tenant}.cosethub.com/api/v1/users/101/groups"
```

## View access

View grants are stored with the view (product: `WarehouseViewRoles` + owners). These endpoints expose that ACL without rewriting the whole view definition.

### `GET /warehouses/{warehouseId}/views/{viewName}/access`

| | |
| --- | --- |
| **Status** | Planned (today: embedded on `GetWarehouseView`) |
| **Scopes** | `permissions:read` |

#### Response `200 OK`

```json
{
  "warehouse_id": 7,
  "view_name": "ref.fa_trades_by_asset_class",
  "grants": [
    { "principal_type": "group", "principal_id": 12, "access": "read_write" }
  ],
  "owner_user_ids": [101],
  "updated_at": "2026-08-05T18:00:00Z"
}
```

If `grants` is empty and there are no special restrictions, the product may treat the view as open to users who can use Database Views — confirm effective access with [`GET /permissions/effective`](#get-permissionseffective).

## Effective permission

### `GET /permissions/effective`

Return the caller’s effective access for a resource (after group membership and owners).

| | |
| --- | --- |
| **Status** | Planned (today: `GetResourcePermissionLevel` / `GetWarehouseScreenAccessPermissionLevel`) |
| **Scopes** | `permissions:read` |

#### Query parameters

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `resource_type` | `string` | Yes | `table` or `view` |
| `warehouse_id` | `integer` | Yes | Warehouse ID |
| `resource_name` | `string` | Yes | Table or view name |

#### Response `200 OK`

```json
{
  "resource_type": "table",
  "warehouse_id": 7,
  "resource_name": "ref.equity_master",
  "access": "read_write",
  "matched_via": "group",
  "group_id": 12
}
```

| Field | Description |
| --- | --- |
| `access` | Effective level (`no_rights`, `read_only`, `read_write`) |
| `matched_via` | `group`, `owner`, `warehouse_default`, or `none` |
| `group_id` | Present when `matched_via` is `group` |

## Typical admin flow

1. **Create a group** — `POST /groups` with the users who should share access.
2. **Grant the table** — `PUT .../table-access/{tableName}` with that group at `read_only` or `read_write`.
3. **Grant the view** — `PUT .../views/{viewName}/access` with group grants and/or `owner_user_ids`.
4. **Move people later** — `PUT /users/{userId}/groups` (or patch the group’s `user_ids`) without re-touching every table policy.
5. **Verify** — `GET /permissions/effective` as a token for that user (or inspect membership + policies).

## Errors

| HTTP | `code` | When |
| --- | --- | --- |
| `400` | `bad_request` | Invalid `access`, empty name, malformed grants |
| `403` | `forbidden` | Caller lacks permission to manage ACLs |
| `404` | `not_found` | Unknown group, user, warehouse, table, or view |
| `409` | `conflict` | Duplicate table policy / group name |
